# 附件按范围读取与历史快照复用

按前端请求、适配读取、模型接收整条链路定位。本轮确认的重复 IO 在 Harness adapter；前端 transport 已校验分块长度、偏移、媒体类型和取消信号，底座发送仍需完整附件。会话 worker 仍拥有正文与附件归属，AttachmentStore 仍通过现有 v4/attachment/read 提供分块。无底座、模型、前端协议或持久化格式改动。

## 附件读取

读取流程：消息归属及 row/index 校验 → 范围校验 → 解析会话内提交引用或原绝对路径 → 打开文件 → 从同一个文件句柄检查普通文件和 20MiB 上限 → 必要时读取图片头检查原 MIME 签名 → 仅读取请求范围 → finally 关闭句柄。

复用 resolve 的引用定位方法，避免形成另一套路径规则；模型发送/prepare 仍需要完整内容并保持现有行为。范围上限仍为 512KiB，返回 dataBase64/mediaType/totalBytes/nextOffset。EOF 外请求返回空内容，空文件保持可读，未授权消息或跨会话引用仍拒绝。中途发生短读先继续读取，真正提前 EOF 表示文件已变，报错而不返回填零的伪数据；错误也关闭句柄。每块最多读请求字节及最多 12 字节的图片签名，不为预览计算完整文件哈希。

文件可以在两次请求间变化，不新增长期文件缓存或声称完整下载具有跨请求快照隔离。验证同长度修改下一次可见；普通文件、超限、图片签名、缺失文件、短读与异常关闭均回归。

## 历史读取

session/read 非 primary 路径一次读取同时获得 session 和 rows，避免两次读取、解析以及可能把不同时间点的元数据和正文组合。primary 仍使用内存且不读盘；不存在的 session 保留 -32002，自定义标题与历史可见消息投影不变。

## 验收

受控 4MiB 文件按 512KiB 八块完整读取，前后 bytes/base64/offset 结果一致，完整文件读取量从 32MiB 降至 4MiB。验证 committed 和 localPath 两种来源。历史读取首次统计读数 2→1，活动会话 0。真实候选软件用 Step Plan 订阅发送图片附件、读取图片内容，重启打开消息并验证预览；异常与大文件边界由自动测试覆盖。
